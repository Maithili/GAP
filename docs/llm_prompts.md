# LLM prompts — one rendered example of each

Every LLM call in this repo comes from one of **three** files. This document shows a
real, fully-rendered example of each prompt: the system message, the user message, and
the strict JSON response schema the model is forced into.

These were generated by calling the actual prompt builders on HouseholdA data — they are
not paraphrases. Regenerate after editing any prompt.

| # | Prompt | Used by | Model | Source |
|---|--------|---------|-------|--------|
| 1 | Day curation | **Hybrid** robot, *train time only* | `gpt-4o` | `agents/llm_memory_curator.py:86-171,299-329` |
| 2 | Relocation prediction | **Plain-LLM** robot, every tick | `gpt-4o-mini` | `agents/robot_policy_plainllm.py:29-35,155-186,211-220` |
| 3 | Object found elsewhere | **LLM human**, branch B | `gpt-4o-mini` | `agents/llm_human_prompt.py:251-285` |
| 4 | Object already at destination | **LLM human**, branch A | `gpt-4o-mini` | `agents/llm_human_prompt.py:288-320` |
| 5 | Observe robot action — `redirect` | **LLM human**, audit hook | `gpt-4o-mini` | `agents/llm_human_prompt.py:323-377` |
| 6 | Observe robot action — `undo_allow` | *deprecated* mode of the same hook | `gpt-4o-mini` | `agents/llm_human_prompt.py:323-377` |

Two things that surprise people:

- **GAP makes zero LLM calls at evaluation time.** The curator (prompt 1) runs only inside
  `train()`. Prompts 3-6 are the *user model*, not the robot.
- **NOPA and SLaTe-PRO and STREAK have no prompts at all.** In a NOPA run the only LLM is
  the human (prompts 3-6).

Prompts 3-6 share one system message and are assembled from four helpers —
`_format_event`, `_format_day_history`, `_format_examples`, `_format_upcoming_plan`
(`agents/llm_human_prompt.py:176-249`) — plus few-shot examples loaded from
`config/llm_human_examples.json`.

Pricing for every cost estimate comes from `_MODEL_PRICING_USD_PER_1M`
(`agents/llm_human_prompt.py:39-43`).

## 1. Day curation — hybrid robot (train time)

Segments one warm-up day's relocation stream into named activity episodes, with **no
ground-truth labels**. Output builds the task graphs the particle filter runs on. Called
once per warm-up day from `MemoryCurator.curate_day`; on an unusable answer the same user
message is re-sent with the invalid response appended (`agents/llm_memory_curator.py:351-355`).

The running vocabulary shown below is illustrative; in a real run it accumulates from the
days already curated.

**System message** (1054 chars)

```text
You annotate a single person's household routine from object-relocation logs (the only sensor available — no vision, no audio). Each line is one observed move: time, object, from-location -> to-location. The day runs 06:00-24:00. Your job: partition the day's numbered events into contiguous segments, each corresponding to one activity episode (e.g. a meal, dishwashing, getting ready), and name each segment with a short snake_case activity name. REUSE an existing vocabulary name whenever the episode is the same kind of activity; create a new name only when nothing in the vocabulary fits; propose a merge when you realize two vocabulary entries denote the same underlying activity; propose a rename when an existing name no longer describes what you have observed (e.g. cereal_for_breakfast -> cereal_or_oatmeal_breakfast after seeing oatmeal days). Names are encoded by a language model downstream, so make them semantically meaningful and self-describing — say what the person is doing and with what (prefer 'wash_dinner_dishes' over 'cleanup_2').
```

## 2. Relocation prediction — plain-LLM robot

Sent on **every 10-minute tick**. The past-days block is fixed at `train()` time; only
the "today so far" block and the clock change between ticks. When the person has not moved
anything yet, that block is replaced by a morning-idle sentence.

The schema enum is built per household from the live graph — 61 movable objects and 85
destinations for HouseholdA. `home` is excluded as a destination (it is the graph root, not
a placeable surface).

**System message** (378 chars)

```text
You are a proactive household robot living with one person. You watch where they move objects each day. Learn their routine from the past days of observations, then — given today's observations so far — predict which objects they will need moved next and where, so the robot can pre-place them. Predict only moves that genuinely help the person's routine right now or very soon.
```

## 3. Object found elsewhere — LLM human (branch B)

Fires when the human reaches a script line and the object is **not** where they planned
to put it — usually because the robot moved it. `correct` and `accept` both cost the human
a decision; `skip` drops the line.

**System message** (357 chars)

```text
You are simulating a human in a household where a robot assistant sometimes acts on its own. When the robot's action diverges from your plan, decide what the human would actually do. Adapt naturally: sometimes correct the robot, sometimes go along with what it did, sometimes skip the planned step entirely. Output one decision and a one-sentence rationale.
```

**User message** (2043 chars)

```text
Current activity: computer_work
You planned to move the laptop to desk.
But you find the laptop is currently at sofa.

The robot just moved laptop to sofa.
Your upcoming planned actions:
  07:40 move laptop -> desk  <-- this object
  08:40 move notebook -> desk
  11:40 move plate -> table

Day history so far:
  06:30 human moved cereal -> table (did it as usual)
  06:35 robot moved bowl -> sink
  06:40 human moved milk -> table (did it as usual)
  07:10 human moved bowl -> sink (nothing to do, robot already handled it)

Use your upcoming plan to judge whether you still need this object soon. If you have no remaining planned use for it, its current spot is usually fine even if it's not where you'd normally keep it. Only intervene if its placement actually gets in the way of something you still plan to do.

Examples of how this human acted in similar situations:

Example 1:
Current activity: breakfast.
You planned to move the cereal box to the table.
But you find the cereal box is currently at kitchen_counter (the robot already brought it out).
The robot just moved cereal to kitchen_counter.
Decision: accept. Rationale: Cereal at the counter still works for breakfast; not worth moving it the last step to the table.

Example 2:
Current activity: cooking.
You planned to move the spoon to the cookingpot.
But you find the spoon is currently at table (the robot put it on the dining table).
The robot just moved spoon to table.
Decision: correct. Rationale: You actively need the spoon in the pot right now; the table location blocks the task.

Example 3:
Current activity: idle.
You planned to move the remote_control to the sofa.
But you find the remote_control is currently at tvstand (the robot stowed it).
The robot just moved remote_control to tvstand.
Decision: skip. Rationale: Tvstand is fine for the remote; no reason to move it back just to follow the plan.

Decide: 'correct' (put it back where you planned), 'accept' (adapt your activity to use it where the robot put it), or 'skip' (this step is no longer needed).
```

## 5. Observe robot action, `redirect` mode — LLM human

The audit hook, called immediately after **every** robot action. This is the only human
model we report (`human.llm.observe_mode: redirect`). Note the emphatic instruction that the
upcoming-plan list is COMPLETE for the window — without it the model invents needs from the
current activity and undoes far too much.

**System message** (357 chars)

```text
You are simulating a human in a household where a robot assistant sometimes acts on its own. When the robot's action diverges from your plan, decide what the human would actually do. Adapt naturally: sometimes correct the robot, sometimes go along with what it did, sometimes skip the planned step entirely. Output one decision and a one-sentence rationale.
```

